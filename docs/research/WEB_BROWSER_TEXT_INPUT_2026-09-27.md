## Sources And Findings

The screenshot browser previously accepted physical keyboard and paste events on a noneditable div. Its `isComposing` guard did not provide a real host editing surface that could start a system IME. Browser state did not identify an editable target. Blindly focusing a hidden textarea on every viewport click would also activate text input for buttons and other noneditable controls.

[CDP Input](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Input.pdl) distinguishes physical key dispatch, committed non-key text such as IME/emoji, and remote pre-edit composition. [Chromium's input handler](https://raw.githubusercontent.com/chromium/chromium/main/content/browser/devtools/protocol/input_handler.cc) sends `insertText` to the currently focused widget, without an expected target node. [Blink's composition controller](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/core/editing/ime/input_method_controller.cc) can delete the current selection when an empty composition command is sent with no native composition. Generic remote cancellation after focus changes is therefore not harmless.

The installed xterm `CompositionHelper` uses a real textarea and delays final DOM-value reading. This informs a small local event transaction, not reuse of terminal-specific private DI or a second terminal. [UI Events](https://www.w3.org/TR/uievents/#events-compositionevents) describes composition order and the effect of cancelling its starting keydown.

## Interaction And Ownership

The existing native BrowserSession owns a fixed readonly isolated-world focus probe, lifecycle listeners and the existing command serialization. It projects only an opaque owner, editable kind and field anchor rectangle. It never returns field values, passwords, selectors, DOM identifiers or a client-supplied script. A native document/context, editable root and focus epoch determine the owner; returning from A to B to A does not revive A's old receipt. Selection changes refresh the anchor without inventing a new focus phase. Unsupported targets stay unknown; confirmed noneditable controls use null.

Native mouse-up and Tab receipts, state reads and focus/selection wakeups refresh this fact. Navigation and context destruction invalidate it, including same-URL replacement. A supplied owner on text or proxy editing keys is rechecked against actual focus before native dispatch. Invalid owners fail HTTP validation; stale or unknown owners reject admission without refocusing or replaying input. A selection wake can invalidate an in-flight readonly probe while focus remains unchanged: the manager permits at most two probe attempts within the same native context, before any input dispatch. Context replacement exits immediately. Ownerless physical keys and legacy text remain compatible. This receipt is a concurrency check, not new authorization or permanent permission.

The viewport now contains a real, positioned textarea. Only a confirmed editable receipt permits proxy focus; late receipts cannot take focus from the address bar. Keyboard entry uses an existing confirmed target, while pointer entry waits for its native receipt. Owner changes replace the actual textarea node so late native events from the old field cannot be reused at the new field.

Normal physical keys retain `keyDown{text}` semantics, allowing the remote page to prevent insertion. Process/229/Dead/AltGraph/Option and composition input use the host editing surface. Candidate keys have local down/up ownership; ordinary keys remain paired with their remote down. Composition commits read the final unsent DOM range once, including engines that emit final input after compositionend. Position-based accounting accepts repeated equal text and emoji without string-based deduplication. Already-ended input flushes before a new composition, ordinary Enter, paste or normal blur; unfinished or invalidated input is discarded. Non-keyboard delete/newline commands carry the same owner on both down and delayed release.

A later successful character cannot repair an earlier rejected insertion. Owned-input failures remain visible within their captured navigation, focus-intent and active scope, without requiring them to be the newest character request. Subsequent successful characters, ordinary keys or scrolling do not erase them. Explicit pointer entry, Tab, navigation and valid paste clear displayed feedback; late failures outside the original scope do not reappear. This uses the existing error state and lifecycle counters, not a new latch or error queue. Native input is never replayed to recover missing text.

There is no separate insertion form, new Session storage, arbitrary browser execution tool, native remote pre-edit, remote cancellation, model call or automatic failed-input replay.

## Limits

Admission checks and CDP insertion are not atomic against page JavaScript changing focus or caret between commands. The existing manager orders its own commands, not arbitrary page execution. A successful CDP command is not proof that an application accepted or persisted the text. The probe does not expose a generic precise input/textarea caret; candidate anchoring uses the field rectangle. Passwords have no committed-text proxy because a plain textarea would retain an unmasked local value; legacy physical key and paste paths remain. Closed shadow roots, cross-origin/OOP frames and transformed iframe geometry remain unknown rather than guessed.

Only final committed text is forwarded. Remote editors do not receive the host's complete pre-edit composition lifecycle, so this is not full native IME parity. Synthetic event tests and Unicode automation do not establish a real macOS candidate window, Safari IME, or a physical iOS/Android keyboard/user-activation path. Browser E2E is excluded at the user's request. No native Codex UI comparison is claimed: the Computer Use tool again explicitly denied access to `com.openai.codex`. The installed tool's public `computer-use-policy.js` maps this exact error to the native service's `forbidden` decision, before user approval; organization-policy `denied` has a distinct message. The specific rule and removal mechanism remain unknown. The broad Web interaction work remains open in #597.
