## 这次为什么反复返工

主要原因是实现顺序和证据使用错误：先把功能塞进既有 OpenPI 组件，再寻找 Codex 的相似依据；没有先固定控件位置、实际分支和状态变化。功能测试检查了我们的实现，却没有独立检查它是不是用户要的界面。前一轮 24 项浏览器测试通过以后，用户仍然能用两张截图指出明显差异，说明这些测试不能作为视觉一致的证据。

以下记录包括此前几轮已经发生的返工，以及本次新发现的问题。用户截图、源码事实、静态推断和本地验证分开记录；不把未观察到的 Codex 实时行为写成已经复现。

## REA 调查本身踩过的坑

1. **第一次直接分析整个 ASAR，范围过大。** 安装包约 562MB、20,915 个成员；先遇到 unpacked 原生成员完整性问题，后一次等待 300 秒超时且没有可用保留记录。两次都不能算“分析了整个 App”。后来改为四个原样提取模块的有界分析，再对根 bundle 做具体函数与调用点检查。
2. **保留的 Evidence ID 绑定连接。** 后续连接找不到旧 ID，不能因此重跑大型分析，也不能假装读取成功。使用已导出的完整 `rea-evidence.json` 和 `rea inspect-evidence-bundle` 复用记录；记录分析覆盖范围和 unresolved imports。
3. **一个包里有多种 UI 分支。** Electron、browser、旧版、新版、特性开关和共享组件可能具有不同高度、入口与行为。找到 `30px`、`36px`、箭头或菜单项的字符串，不代表它作用于用户截图。必须从侧栏实际调用点追到 props 和条件。
4. **不能将静态代码结论描述成实时观察。** 原生 Codex UI 访问未完成；本次证据来自用户截图与安装包静态代码/CSS。不得绕过已有阻断，也不得把 OpenPI 的测试结果说成已验证 Codex 原生渲染。
5. **截图像素不是 CSS 像素。** 原始截图经过高分屏与消息缩放，截图中的 28px 文字不直接意味着 `font-size: 28px`。应先核对 token，再用已知视口和缩放的本地截图比较相对关系。

## 下次如何避免同类返工

以下是本次复盘提出的方法，不是新增运行时状态机或项目强制约束。

1. 先列用户要求的可见状态，再写实现。至少覆盖普通、选中、悬停、焦点、菜单打开、展开/折叠、长标题、空列表、加载、失败、取消和窄屏；没有依据的状态标为未知。
2. 每个入口留一条证据链：用户截图 → 具体组件调用点 → props/条件 → 图标或 CSS → 操作后的状态。先回答“它在哪里、属于谁、什么条件下出现”，再回答“怎么实现”。
3. 分开记录三种差异：实现错误、受 Web/Pi 能力约束的明确适配、尚未验证。不能把所有差异都事后叫作“Web 适配”。44px 触屏目标是适配；品牌菜单换用途和项目行凭空换箭头是错误。
4. 先做一个完整的项目行和一组真实菜单，逐状态对照，再扩展到所有列表。复用旧组件之前先检查它携带的隐藏交互和 CSS；不要仅因名称相近就继承。
5. 用真实浏览器验证最终 DOM 与样式层叠。尤其检查 portal、媒体查询、通用组件规则、`!important`、触屏/细指针组合、菜单关闭后的焦点。测试不得只复述实现。
6. 后端从 Pi 和 App Server 的生命周期出发，UI 只投影事实。不要通过红点、标签、当前选中或 Promise 返回来猜测执行成功和阅读完成。
7. 验收报告分别写功能、视觉和未知项。测试数量不能证明“复刻完成”；截图只证明它实际展示的状态，不证明悬停、取消和异步变化。
8. 最后做消融：移除为了猜测而加入的替代入口、重复状态、隐藏 DOM 和冲突覆盖；仍满足原验收目标就删掉。保持来源、测试环境和证据文件可追溯。

这是本次工作的方法修正，不是新增全项目强制协议，也不新增运行时抽象。

| 取消与失败 | 取消只绑定 fork command；创建开始后返回 too-late 并继续等待真正结果。只有所有权、Git 身份、HEAD/index/完整内容仍匹配本次 baseline 才清理；外部改动或不确定目录保留并显示路径。 |
| 项目与权限 | metadata 留在原生分支中。sidebar 用原项目归属，真实 cwd 用于工具、文件、终端、Git、Trust。当前阅读蓝色图标不改变项目顺序；会话导航展开对应项目，之后仍可手动折叠。 |
| 继续分叉与重启 | child ID、cwd、parentSession、原项目和 worktree 信息持久化；从工作树会话继续 message/edit/regenerate 分叉仍保留归属。HTTP command 重放仅保证当前进程内；不声明跨崩溃重放。 |

仍未复刻 Codex 专有 environment/setup UI、setup 失败后“继续/重试”流程、视图布局复制、远程/cloud fork 和工作树自动回收。Pi 的 settings/resources/Trust 仍重新按真实 cwd 读取，不自动信任、不自动安装依赖。源和目标内容双检查不是跨进程全局文件系统锁。实现对 sparse/unmerged/submodules 明确拒绝；32 MiB patch、128 MiB 检查内容、20,000 选中条目及超时是 OpenPI 的限制。当前验证平台为 macOS；Windows、网络文件系统及特殊 Git filters 未实测。
