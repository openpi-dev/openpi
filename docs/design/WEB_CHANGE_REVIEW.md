## 问题与已核对事实

用户截图中的“200 个文件已更改”悬浮入口展开为大面积文件列表，遮住对话，列表底部还需再次点击“审阅更改”。从截图无法判断这些文件是否属于当前轮次，也看不到文件状态、比较基准和清单是否完整。

当前 PR 源码已经没有截图中 Composer 上的悬浮文件清单：全局入口在 `SessionOverview`，按轮摘要在 `TurnChangesCard`。所以不能声称截图就是最新构建，或只通过移动旧按钮修复。接下来的实现必须在当前两个入口和审阅面板上收敛，不恢复旧悬浮列表。57161 的运行时溯源确认 checkout 为上述 OpenPI revision，`pi list` 唯一 OpenPI 来源为独立 web-runtime checkout；未以截图推断浏览器实际加载的资源版本。

源码仍存在的问题与能力边界：

1. `web/protocol/types.ts` 的 `WEB_MAX_GIT_REVIEW_FILES = 200`；`ReviewPanel` 用 `snapshot.files.length` 作总数文案。200 是返回上限，不保证等于完整总数。不能只因数量为 200 就判断发生截断。
2. `snapshot.truncated` 同时涵盖文件清单、diff 字节和快照大小限制。因此只有这个布尔值时，应写“已载入 N 个文件，结果不完整”，不能断言“还有 N 个文件”或“超过 200 个”。
3. 工作区默认范围为 `unstaged`，即未暂存的受跟踪修改及未跟踪文件；不是 staged + unstaged 的所有未提交变更。会话开始后的比较也不是某一轮的比较。
4. `TurnChangesCard` 已绑定原生 prompt ID，每轮只展示有文件的卡片、默认三个文件。但深入审阅仍发生在聊天卡片内；工作区审阅另有一个面板。相同阅读任务存在两套导航。
5. `ReviewPanel` 已有每次 20 行展开、按文件加载 diff、错误/截断提示和返回焦点的基础；可以复用。现有“显示更多”只展开已返回清单，不能读取第 201 个文件。
6. 行数的 `0` 不能一概解释为“无变化”：未加载的未跟踪文件、二进制和未知统计必须区别。现有协议没有完整表达二进制判定和计数完整性。

## 推荐方案：两个语义入口，一个阅读面板

### 1. 回答后的卡片只描述本轮

- 保留此前用户选择：每轮用时在回答顶部；文件摘要在回答后，至多一张。
- 文案用“本轮变更 · 3 个文件”，副说明“该轮开始至结束的工作区差异”。不称“AI 已编辑”，因为期间可能有用户或其他进程修改。
- 默认三行：状态、文件名与可区分的相对目录、已知增删行数；没有可展示文件时不显示卡片。
- 点击某行直接打开该轮该文件；点击“查看本轮变更”打开同一面板，默认首个文件。
- 大批量时底部写“查看全部 N 个文件”，直接进入面板，不在聊天中展开 200 行。部分记录写“查看已记录文件”，避免假总数。
- 已保存的历史轮次始终绑定其 prompt ID、记录版本和保存的 diff。工作区后续修改不能覆盖历史轮次的差异。
- 该轮基线不可用、无可展示文件时：不在普通回答中重复警告，也不伪造“0 文件”；保留原始状态，在主动查看变更详情时说明。

### 2. 工作区入口归属会话工具区

- 沿用当前右上角会话概览，清楚命名“工作区更改”。它直接打开已有 Workbar 的审阅页，不再弹出第二份文件清单。
- 紧凑标记只在计数和范围均明确时显示，例如“未暂存 · 12”；数据不完整用“部分”，未知/失败不给零计数。
- 打开面板后标题是“工作区更改”，范围默认“未暂存（含未跟踪）”。已暂存、分支对比、自会话开始后的变更保留在范围选择中，说明各自基准。
- “本轮变更”是从具体轮次进入的固定历史范围，不把 `session` 改名成 `last turn`。从历史范围切去工作区时显式选择“工作区 · 未暂存”，标题随之改变。
- 不自动把截图中 200 项算成此轮改动；未跟踪的文件也应明确写“未跟踪”。

### 3. 面板阅读与尺寸

- 宽屏使用现有右侧 Workbar。保留聊天和草稿；一次只打开一个审阅内容区。浏览器、终端等现有页签通过原 Workbar 切换，避免叠加第三层弹窗。
- 建议默认审阅宽 480px，可复用现有拖拽机制；当可用布局不能同时容纳约 480px 聊天和 420px 审阅时，改为完整主内容区。按可用容器宽度判断，不仅按设备名称。
- 面板内部默认“清单 → 单文件 diff”，保持一列的阅读密度；详情顶栏显示返回、文件路径、范围、关闭。避免在 480px 内再塞文件树与 diff 两列。
- 返回清单保留筛选词、展开数量、滚动位置和来源行焦点；关闭回到原入口及原聊天位置。从同一轮的另一文件点击，切换选中文件而不多开页签。
- 手机用完整主内容区，顶部“返回对话”；查看文件时“返回文件”。Composer 草稿保留，返回后再恢复输入焦点，不为查看文件主动弹键盘。
- 文件路径在清单中最多两行，文件名优先保留、目录用次要文本；详细页完整路径可换行/复制。同名文件不能只剩相同 basename。数字按自然顺序排序，例如 1、2、10。
- 桌面行高建议 40px，触屏至少 44px；状态采用文字加图标/符号，不只依赖颜色。Escape 在详情先回列表，在列表关闭面板；输入法组合过程中不拦截。

### 4. 文件清单、搜索和差异

- 不默认加目录树和多组状态筛选。单一相对路径搜索足够支持本次大文件清单，按目录与文件名匹配。
- 本地分页每批 20 行，按钮准确写“再显示 20 个”，末批写实际数量；不把剩余总数写成此次展开数。局部搜索只能叫“搜索已载入文件”。
- 目标体验需要能够取得完整清单：在现有只读 Git 接口上补有界分页及清单完整性，不靠把 200 上限无限调大。涉及分页的请求必须绑定同一工作区/范围/结果版本；版本变化时提示刷新，不混合两版。
- 完整计数未取得前，显示“已载入 200 个文件 · 清单不完整”，不显示“200 个文件已更改”。当前协议只有混合 `truncated` 时，使用更保守的“结果不完整”。不提供实际上无法继续读取的“加载更多”。
- 工作区清单加载成功并不代表所有 diff 已读完。点击文件才取差异；已知行数显示 `+N −N`，未知显示“待读取”，不是 `+0 −0`。
- `.stp` 不能仅凭扩展名判定为二进制：STEP 常为文本。根据真实读取结果区分文本、二进制、超限、不可读和无文本差异。二进制显示状态与“无法显示文本差异”，超限显示“差异过大，预览不完整”。
- 重命名显示旧路径 → 新路径；删除文件使用保存的旧侧内容；不可读显示失败与重试，不显示空白 diff。预览/实际结果来源借鉴 Pi Web，但不混进 Git 工作区统计。

## 状态与连续操作

| 状态/事件 | 可见表现 | 交互保证 |
| --- | --- | --- |
| 初次加载 | 面板骨架及“正在读取更改” | 不提前显示 0，立即可以返回/关闭 |
| 完整空结果 | “没有未暂存的更改”等准确范围文案 | 用户主动打开时可见；不在聊天制造空卡片 |
| 非 Git 工作区 | “此工作区不是 Git 仓库” | 不自动初始化仓库 |
| 首次读取失败 | 错误、重试 | 不伪装为空结果 |
| 刷新失败、有旧内容 | 保留旧内容，标“刷新失败，显示上次结果” | 旧计数不声称实时；重试不清空选择 |
| 清单/差异部分可用 | “结果不完整”，说明已知边界 | 不假精确总数、不把未知统计设为零 |
| 搜索无匹配 | “已载入文件中没有匹配项”等限定文案 | 保留搜索框，不误报整个仓库无结果 |
| Git 更新 | 清单摘要可刷新；正阅读的差异保持当前版本并提示更新 | 不自动滚顶、切文件或篡改正在阅读的内容 |
| 选中文件消失 | “文件已不在当前范围中”及返回/刷新 | 不静默打开另一个文件 |
| 切换会话/仓库/范围 | 清空旧身份内容，重新读取 | 慢返回不得覆盖新目标；取消旧读取 |
| 历史本轮记录缺失 | “此轮保存的差异不可用” | 不回退为当前工作区 diff 冒充历史 |

## 机制边界与实现拆分（未实施）

Pi Session / prompt ID 继续拥有轮次身份；既有 `captureGitTurnChanges` 和持久化轮次记录拥有历史证据；Git 只读读取拥有工作区事实。Web 只负责投影、导航和读取取消，不增加模型调用、第二套变更数据库或“哪些文件应归给模型”的推断器。

1. 首先统一入口、标签和审阅阅读布局，复用现有 Workbar、DiffCodePreview 和 focus-return 模式。两个数据来源共用展示，不共用或混淆缓存身份。
2. 清单不完整与 diff 不完整分别表达；只有完整枚举才能给总数。补真实分页前采用保守文案，不能以纯前端展开宣称支持所有文件。
3. 最后验证长列表、历史记录隔离、窄屏、键盘/输入法和旧资源刷新。源码已无截图旧悬浮清单，因此验收必须检查浏览器实际加载版本，不能仅检查源码。

这次设计只涉及查看差异。Codex 的暂存、撤销、提交、审核模型请求有各自写入/执行语义；不为了视觉相似放置没有能力支持的按钮。“查看更改”必须只是读取，不隐式触发模型审核。

## 设计消融

按同一目标走读三个方案：

| 移除项 | 走读结果 | 取舍 |
| --- | --- | --- |
| Composer 上的文件清单浮层及二次“审阅”按钮 | 本轮卡片和会话工具入口仍能到达对应 diff，少一次展开且不遮对话 | 删除 |
| 聊天卡片内部的完整 diff 阅读器 | 同一历史身份仍可在 Workbar 阅读，减少两套返回/加载状态 | 删除，保留摘要三行 |
| 审阅面板内部的永久目录树与多状态筛选 | 相对路径、自然排序、搜索仍能找到目标；窄屏更稳定 | 首版删除 |
| 比较范围标签 | 同名文件可能来自历史轮次、索引或工作树，无法知道正在看什么 | 必须保留 |
| 不完整、错误和旧结果状态 | 200 上限与 Git 失败再次被误读为精确总数/无变化 | 必须保留 |

这是设计走读，不是已实现代码的自动化消融。交互示意用于检查入口、范围切换和返回；其数据是合成数据，不是读取私有工作区。

## 验收场景

1. 工作区有 200+ 个旧文件，本轮只改 3 个：回答卡片只出现该轮 3 个，工作区范围不能冒充本轮。
2. 只聊天、只读工具、无法建立本轮基线：不出现空文件卡片和反复警告；不改变持久化事实。
3. 恰好 200 个且完整，与 200 个且截断：文案有区别；diff 超限但清单完整也不能误报清单被截断。
4. 点击摘要中的第二个文件：一次进入该轮该文件；返回仍在原卡片/原列表位置。
5. 同名路径、1/2/10、重命名、删除、未跟踪、二进制、巨大 STEP 文件：状态和文本差异可用性均准确。
6. 搜索命中第 201 项：只有完整分页/服务端搜索支持后才宣称全量搜索；局部搜索边界清晰。
7. 320、390、768、1440px，浅/深色、200% 缩放、软键盘：无页面横向溢出，返回/关闭可达，草稿保留，触控行不重叠。
8. 慢请求、离线、切会话、刷新时文件消失：不串数据、不把失败变成空结果、不丢阅读位置。
9. 新轮开始、并发外部修改、历史压缩后再打开旧轮次：按真实保存证据显示；不把当前工作树当成旧轮 diff。
10. 文件面板和消息输入连续操作：无需关闭巨型弹层才能回到聊天；查看更改无模型调用和文件写入。

以上是后续实施验收清单，本次未声称已全部通过。

## 实施补记：2026-09-30

本节记录随后用户确认实施后的结果，基于 OpenPI `05f1069`。上节“只新增设计”描述的是此前设计轮次，不代表此节实施状态。

用户补充 Codex 文件卡片截图，并明确去掉文件名前的“修改”“新增”等标签。因此实际卡片采用图标、数量与总增删行数的表头、右侧“查看变更”、默认三行路径及右对齐行数；淡化目录，保留清晰文件名。底部沿截图使用“再显示 N 个文件”，展开清单限高 320px。此选择替代原草案中“全部展开直接跳到面板”的交互，不扩大聊天区高度。详细审阅依然进入 Workbar。

- 删除卡片内独立的差异阅读器、加载/失败状态和返回导航；卡片只传递精确原生 prompt ID 和文件路径。`useTurnReview` 读取既有保存记录，验证 Session 与 prompt ID，再投影到共用 `ReviewPanel`。没有新模型工具或存储系统。
- 工作区更改沿用会话概览入口。清单显示相对路径和已知行数，不展示前置状态徽标；完整/已载入计数、局部搜索和自然数字排序区分；文件详情仍提供 Git 状态和来源说明。
- 在原只读 Git 接口上增加有界分页，每页最多 200 文件；最多枚举 10,000 个摘要文件、以 64 个一批读取元数据。超出边界仍明确部分可用，不宣称全量。下一页绑定结果版本；版本变化拒绝拼接，要求刷新。搜索目前覆盖已载入文件，入口明确写出此范围；逐批载入后可搜索新文件。
- 正阅读的差异固定在当前版本，新版本用可操作提示替代自动刷新正文。返回恢复搜索、列表滚动与来源行焦点；显示旧结果的失败状态不会被当成无变更。手机复用现有 Workbar 全内容区与返回机制。
- 新增二进制事实来自 Git numstat 或实际内容检查；`.stp` 扩展名本身不决定预览。未知行数与二进制不显示虚构的 `+0 −0`。旧轮次记录继续可读，二进制标记为可选字段。
