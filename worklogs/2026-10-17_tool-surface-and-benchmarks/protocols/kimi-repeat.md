# 任务：OpenPI vs 纯 Pi 重复对照（Kimi，TB4 两题 × 5 次）

## 要回答的问题
上一轮五题单次跑里，OpenPI 1/5，纯 Pi 2/5，差距只来自 HTML 一题。
这一轮只回答一个问题：在有区分度的题上重复多次后，OpenPI 的通过率是否稳定低于纯 Pi？
本轮不改任何代码，不调提示词，不评价 Kimi CLI。

## 固定条件（与上一轮 openpi-pi-kimi-tb4-5tasks-20261023 完全一致）
- 模型 kimi-1021-preview，thinking=high；每题限时 15 分钟；Terminal-Bench 4.0、Harbor、镜像都用上一轮的版本。
- OpenPI 和 Pi 的版本沿用上一轮冻结的 commit 和版本号。在 summary 里写出具体的 commit 和版本号，并用 `pi list` 证明 OpenPI 只有一个来源。
- OpenPI 用默认配置。不要改 setup，不要追加系统提示。
- 如果上述任何一项无法复现，停下来报告，不要替换。

## 题目与组别
- 题目：上一轮的 HTML / XSS 过滤、会话窗口修复，两题都用同一个 task id。
- 组别：纯 Pi、OpenPI 两组。
- 每组每题 5 次，共 20 个 trial。
- 运行顺序：按"题 × 轮次"配对。每对的两组前后紧挨着跑，先后顺序逐轮交替。全部在一个连续时间窗口内跑完。
- 可以有限并发，但同一对的两个 trial 必须在同一并发条件下运行。

## infra 失败
- 以下情况算 infra 失败：provider 返回 4xx/5xx 或断流导致运行中断、容器或 Harbor 自身故障。
- 出现 infra 失败时，这一对的两个 trial 都作废，并在同一窗口内一起重跑。只允许这种情况重跑。
- 已经正常判分的失败一律不重跑。
- 模型自己写错代码、超时，都算有效失败。

## 每个 trial 记录
- reward、各项检查的通过数/总数、墙钟时间、是否超时；
- 父会话的模型请求数、累计输入 token、输出 token；超时 trial 的 token 只是下限，要标明；
- OpenPI 组额外记录：subagent_spawn、subagent_wait、subagent_send 的调用次数；第一次 spawn 和第一次 wait 发生在第几分钟；wait 阻塞的总时长；子会话的请求数和输出 token；是否用了 workflow；
- 首轮请求的输入 token 和工具数量，作为固定开销的核对，预期 OpenPI 比纯 Pi 多约 1.5k。

## 失败归类（每个失败的 trial 只能归一类）
1. 代码缺陷：按时交付了，但没通过检查。注明是哪类缺陷，HTML 题注明是否又是解析器异常没兜住。
2. 等子代理超时：超时时父会话正阻塞在 subagent_wait 里。
3. 探索未收敛：超时时没有在等子代理，正式产物没完成。
4. infra：作废。

## 判定（跑前定死，跑完不许改）
每组 10 个有效 trial，用 OpenPI 通过数减纯 Pi 通过数：
- 有退化迹象：总差 ≤ −3，或 HTML 单题差 ≤ −3。
- 无退化证据：总差 ≥ −1，而且 HTML 单题差 ≥ −2。
- 其余情况判"不确定"。

另外，无论判定结果如何，都要单独报告：
- OpenPI 有多少个 trial 用了子代理；用了和没用的两类 trial 各自的通过率；第 2 类失败（等子代理超时）出现了几次。
- 如果判"有退化迹象"，说明失败主要落在哪一类。
- summary 里写明：每组 10 个 trial 属于筛查级样本，不是统计显著性结论。

## 不要做的事
- 不修改 OpenPI 或 Pi 的代码，不加或改提示词，不换模型、推理档位、限时或题目。
- 不加组，包括 Kimi CLI 和任何消融组。下一步做什么由我决定。

## 交付
- 归档目录：benchmarks/openpi-pi-tb4-repeat-<日期>/。内容包括：每个 trial 的 CSV、配对表、失败归类表、判定结果、作废记录、冻结的版本标识；每个 trial 的原始会话都要保存，包括子会话。
- 归档前做凭据扫描，不要归档任何密钥。
- summary 第一行直接写判定结果：有退化迹象 / 无退化证据 / 不确定。然后写两组每题的通过数，再写子代理使用情况和失败归类。
- 回报时给出 summary 的路径。
